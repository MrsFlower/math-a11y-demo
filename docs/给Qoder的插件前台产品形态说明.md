# 给 Qoder 的插件前台产品形态说明

更新时间：2026-07-31

## 结论

当前项目的主产品形态，不是独立网页工具，也不是先做桌面软件，而是：

> **浏览器插件作为前台，Web 服务作为理解引擎和调试台。**

这意味着用户真正接触的是插件；网页只是演示、调试、回归和深度查看的地方。

我们要沿用之前手机项目的交互思路，但不照搬设备形态。核心方法是：

- 先在用户当前阅读环境里捕获公式。
- 先让用户确认识别结果。
- 再生成解释和追问。
- 最后保存历史，便于回看。

未来如果扩展到移动端，可以直接复用这套交互骨架。

## 为什么是插件前台

### 1. 公式本来就出现在网页里

教材、网课、论文、在线文档、作业平台，很多公式都在浏览器里。插件可以直接拿到：

- 当前页面 DOM
- 选中文本
- MathML
- 复制内容
- 右键菜单目标

这比先把用户拉到一个独立网页里更自然。

### 2. 插件更接近真实使用路径

视障用户遇到公式时，通常不是主动打开一个新工具，而是在原页面里卡住。插件前台的意义是：

- 不切应用
- 不复制一大串复杂内容到别处
- 不打断当前阅读

### 3. Web 端更适合作为调试和演示台

我们现在的 Web 服务已经很强，适合做：

- 结果详情页
- 调试页
- 回归测试页
- demo 演示页
- 管理和诊断页

但它不应该是用户日常触达的唯一入口。

## 产品定位

### 当前主定位

**公式理解前台助手。**

它不是通用阅读器，不包办整篇文档，也不做完整 OCR 平台。它只接住一个具体问题：

> 用户在当前页面看到了一个公式，但看不懂，需要把它快速送进一个可确认、可解释、可追问的理解流程。

### 目标用户

1. 视障学生。
2. 视障教师。
3. 特教老师。
4. 无障碍志愿者。
5. 先由非视障用户试用，再逐步找真实共创者验证。

## 交互骨架

请把整个产品做成下面这条稳定链路，不要偏：

1. 捕获公式。
2. 用户确认识别结果。
3. 生成短讲解。
4. 展示详细解释。
5. 支持追问。
6. 支持复制和保存。
7. 支持历史回看。

这是跨插件、网页、未来移动端都可复用的骨架。

## 插件前台应该承担什么

插件不是单纯的按钮入口，而应该是前台本体。它要负责：

- 触发
- 捕获
- 第一屏显示
- 确认
- 追问
- 保存
- 状态反馈

### 插件前台必须有的能力

#### 1. 触发

至少支持以下 3 种：

- 选中公式后触发
- 右键菜单触发
- 快捷键触发

可选再加：

- 页面浮动按钮

#### 2. 捕获

优先支持：

- 当前选中文本
- 当前页面中可提取的 MathML
- 当前页面 DOM 中的公式节点
- 复制到剪贴板的公式文本

后续再考虑：

- 截图 OCR
- 网页插件外的系统捕获

#### 3. 第一屏显示

插件弹出的不是完整页面，而是一个小型卡片或侧边面板，先显示：

- 识别到的公式名称
- 置信度
- 一句话用途
- 是否需要用户确认

#### 4. 确认流程

识别结果必须先让用户确认，再进入分析。

常见操作：

- 修改识别结果
- 重新提取
- 确认并分析
- 只复制识别结果

#### 5. 解释与追问

分析完成后，插件前台至少显示：

- 公式用来做什么
- 直觉解释
- 变量说明
- 详细解释入口
- 追问入口

#### 6. 保存和回看

插件要支持本地历史记录：

- 最近分析过的公式
- 最近的解释摘要
- 复制和重新打开

## Web 端的角色

Web 端不是主前台，而是三类辅助页面：

### 1. 调试台

用来测试：

- 输入识别
- 公式解析
- 模板命中
- 解释质量
- 追问质量

### 2. 演示台

用来展示：

- 复杂公式解释
- 结构树
- 详细概念层
- 评估样例

### 3. 兜底输入页

当插件暂时抓不到内容时，用户可以回到 Web 页：

- 粘贴 LaTeX
- 粘贴普通文本
- 上传图片
- 查看历史

## 输入方式的优先级

插件前台必须优先服务“从当前阅读环境送入公式”。

### 第一优先级

- 选中公式发送
- 当前页公式提取
- 右键菜单发送

### 第二优先级

- 复制后粘贴到插件
- 普通文本转公式
- 分享图片 / 截图

### 第三优先级

- OCR
- 手动编辑

### 不要作为主路径

- 强制用户手动输入 LaTeX
- 让用户先学会公式语法再用产品
- 让用户在独立网页和原页面之间来回切换

## 视觉与交互原则

插件界面要轻，不要做成重型网页。

### 推荐结构

1. 顶部状态区。
2. 当前公式预览。
3. 确认 / 重新提取 / 复制按钮。
4. 一句话总结。
5. 详细解释折叠区。
6. 追问输入框。
7. 历史记录入口。

### 交互要求

- 先短后长
- 先确认后分析
- 先结果后细节
- 默认不铺满全部内容
- 所有关键操作有明确按钮名
- 所有状态有可读文本

### 无障碍要求

- 全键盘可用
- 焦点顺序清楚
- 状态区能读
- 折叠区能展开
- 表格和列表要是真结构，不是假卡片

## 技术边界

### 插件先做什么

1. 捕获当前公式。
2. 把内容送到现有 Web API。
3. 接收解释结果。
4. 以卡片形式显示。
5. 支持复制、追问、历史。

### 插件暂不做什么

- 不做完整桌面软件壳
- 不做系统级全局抓取
- 不做复杂公式编辑器
- 不做浏览器之外 App 的接管
- 不做完整 OCR 主链路

### Web 端继续保留什么

- 后端理解引擎
- 长解释页面
- 评估脚本
- 诊断页面
- 回归测试

## 与手机项目的关系

这套逻辑可以借用手机项目的思路，但不要照搬载体。

可借用的部分：

- 伴随式助手
- 当前页面捕获
- 先确认再分析
- 状态诊断
- 历史回看
- 轻量悬浮入口

不必照搬的部分：

- Android 悬浮窗
- 手机系统权限链
- 移动端全局捕获

未来如果做移动端，插件的交互骨架可以直接迁移。

## 本阶段任务

请按下面顺序推进：

### 1. 定前台结构

输出一份插件前台信息架构：

- 触发区
- 识别确认区
- 解释区
- 追问区
- 历史区

### 2. 定第一屏内容

插件第一屏必须解决：

- 我捕到了什么
- 识别准不准
- 要不要我确认
- 下一步是什么

### 3. 定状态流

至少定义这些状态：

- 空闲
- 捕获中
- 识别待确认
- 分析中
- 已完成
- 失败可重试

### 4. 定交互细节

明确以下细节：

- 触发方式
- 第一屏卡片大小
- 展示顺序
- 确认按钮位置
- 追问入口
- 复制入口
- 历史入口

### 5. 定 Web 端保留能力

Web 端只保留：

- 调试
- 演示
- 兜底输入
- 深度查看

## 推荐实现顺序

1. 先把插件的 UI 骨架定下来。
2. 再接现有 Web API。
3. 再做当前页公式提取。
4. 再做选中发送和右键菜单。
5. 最后再考虑 OCR 和更复杂的输入。

## 验收标准

完成后，至少满足以下条件：

- 插件能作为用户的主要前台使用。
- 用户不需要先打开 Web 页再开始。
- 识别结果先确认，再分析。
- 第一屏就能看到公式、用途和下一步操作。
- Web 页仍可作为调试台和演示台。
- 这套骨架后续可以迁移到移动端。

## 最后一句

我们不是做一个“网页解释器”，而是在做一个“公式理解前台”。  
插件是前台，Web 是后台和演示台。这个边界要从现在开始定死。
