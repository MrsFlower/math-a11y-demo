- 空选区、受限页面等失败场景会打开手动粘贴兜底，并把焦点送到输入框。

## 二、用户测试暴露的问题

这轮 UI 简化只是把复杂选项藏起来了，还没有彻底把任务流重构成用户视角。

用户反馈的关键问题：

1. 首页主按钮已经叫 `转译选中公式`，但 `换一种方式` 中仍有 `转译原文，不解释` 这种重复概念。
2. 用户点击转译结果中的 `转去理解模式` 后，并没有直接开始理解。
3. 当前流程会提示：

   ```text
   转译结果转理解（已自动转换）捕获成功，正在生成朗读预览。
   焦点已在「确认并分析」按钮，按回车开始分析；需修改请按 Shift+Tab 进入编辑框。
   ```

4. 用户还需要在折叠区里找到识别结果，再点击 `确认并分析`，才能进入下一步。
5. 对视障用户来说，这等于从“我想进一步理解”被拉回到开发者流程：
   - 转译
   - 转换 LaTeX
   - 确认 LaTeX
   - 分析

结论：当前 UI 仍在暴露实现细节，尤其是“模式切换”和“确认 LaTeX”不应该成为正常路径中的必经步骤。

## 三、对产品需求的重新梳理

用户真正需要的不是选择工作模式，而是完成三个任务：

1. **读出来**：我现在读不懂这个公式，帮我把它转成读屏友好的文字。
2. **讲明白**：我已经听到了公式，但还不理解，帮我解释它。
3. **拿不到时兜底**：当前页面或选区拿不到内容，给我粘贴、扫描等替代入口。

因此下一版 UI 不应继续围绕“转译模式 / 理解模式 / 识别确认”组织，而应围绕任务状态组织：

- 首页：获取当前公式并读出来。
- 转译结果页：围绕当前公式继续操作。
- 需要确认时：只在识别不可靠时显示确认。
- 更多：放不常用入口和调试入口。

## 四、建议的下一版 UI 结构

### 1. 日常首页

只保留最少入口：

- 状态提示
- 主按钮：`转译选中公式`
- 次入口：`粘贴公式`
- 低优先级折叠区：`更多`

首页不再展示：

- `转译原文，不解释`
- `理解公式，可追问`
- `转译风格`
- `提取本页公式`
- `确认识别结果`

这些内容不应打断用户第一步。

### 2. 转译结果页

转译完成后，结果页应成为新的当前上下文。

建议结构：

- 标题：`转译结果`
- 转译后的可读文本
- 主按钮：`进一步讲解这个公式`
- 次按钮：`复制结果`
- 次按钮：`重新选择公式`

这里的主按钮必须直接进入讲解流程，不应让用户去折叠区里找确认按钮。

### 3. 讲解流程

点击 `进一步讲解这个公式` 后：

- 如果原始输入可以高置信度转成 LaTeX：
  - 直接开始分析。
  - 状态播报：`正在讲解这个公式。`
- 如果识别置信度中低：
  - 显示一个临时确认区。
  - 标题：`识别结果需要确认`
  - 主按钮：`确认并讲解`
  - 确认区直接出现在当前流程下方，不放在 `更多` 里。

这可以把“确认 LaTeX”从常规必经流程降级为异常处理流程。

### 4. 更多折叠区

`更多` 只保留非日常路径：

- 扫描本页全部公式
- 手动粘贴
- 切换转译风格
- 修改快捷键默认行为
- 服务设置
- 打开测试页

这里的定位是“换入口 / 调设置 / 做测试”，不是完成主流程的必经部分。

## 五、建议的代码改造点

### 1. 去掉工作模式单选框作为主状态

当前代码依赖：

- `currentMode()`
- `applyMode()`
- `input[name="work-mode"]`

下一版建议不要让 UI 直接暴露工作模式。内部可以保留状态，但用户不应该看到“转译 / 理解”二选一。

### 2. 重构 `转去理解模式`

当前函数：

```javascript
function transcribeToExplain() {
  if (!lastTranscription) return;
  const radio = document.querySelector('input[name="work-mode"][value="explain"]');
  radio.checked = true;
  radio.dispatchEvent(new Event("change"));
  $("transcribe-section").hidden = true;
  handleIncomingText(lastTranscription.original, "转译结果转理解");
}
```

问题是它复用了旧的 `handleIncomingText -> enterConfirm -> analyze` 路径，所以必然把用户带回确认框。

建议改为新函数：

```javascript
async function explainFromTranscription() {
  if (!lastTranscription) return;
  // 1. 用 lastTranscription.original 转 LaTeX
  // 2. 高置信度则直接 analyzeLatex(latex, sourceNote)
  // 3. 中低置信度才显示 confirm box
}
```

同时把按钮文案从 `转去理解模式` 改为：

```text
进一步讲解这个公式
```

### 3. 拆出可直接分析的函数

当前 `analyze()` 从 `confirm-input` 读取 LaTeX。建议拆成：

```javascript
async function analyzeLatex(latex, sourceNote) {
  // 原 analyze 主体逻辑
}

async function analyze() {
  await analyzeLatex($("confirm-input").value.trim(), "用户确认结果");
}
```

这样高置信度自动转换后，可以直接调用 `analyzeLatex()`，不必制造一个确认框让用户再按一次。

### 4. 确认区移出折叠区

当前 `confirm-box` 在 `alternate-actions` 里面，导致用户从主流程进入理解时还要进入折叠区找按钮。

下一版建议把 `confirm-box` 放到主内容区，作为异常状态显示。

### 5. 调整状态播报

当前播报“捕获成功，正在生成朗读预览，焦点在确认按钮”仍是旧流程文案。

下一版应区分：

- 直接分析：
  - `已识别公式，正在讲解。`
- 需要确认：
  - `识别结果需要确认。焦点已在「确认并讲解」按钮。`
- 转译完成：
  - `转译完成。焦点在「进一步讲解这个公式」按钮，也可以复制结果。`

## 六、测试页是否放入加载项包

测试页当前已经存在：

```text
static/plugin_test_page.html
```

服务侧已经挂载：

```text
http://127.0.0.1:8321/static/plugin_test_page.html
```

并且 `setup.py` 会把 `static/*.html` 打进后端服务包。

结论：**不建议把测试页塞进 Chrome 扩展加载项包里。**

原因：

1. 插件要测试的是普通网页上的选区、DOM、MathJax、KaTeX、MathML 等捕获能力。
2. 如果测试页放到 `chrome-extension://` 页面里，权限、注入、页面环境都和真实网页不同。
3. 作为后端静态页分发，更接近真实使用场景，也便于云端和本地共用。

建议新增“首次体验入口”，而不是把测试页放进扩展包：

- 首次快捷键设置完成后，提示：`可以打开练习页试一次`
- 按钮：`打开练习页`
- 链接：`${apiBase()}/static/plugin_test_page.html?bust=1`

这个入口可以放在：

- 首次设置保存后的状态提示附近
- 或服务设置 / 更多折叠区中

不要长期放在日常首页，避免污染真实用户的主流程。

## 七、下一步优先级

建议按以下顺序推进：

1. 把侧边栏主流程重构为“首页 -> 转译结果 -> 进一步讲解”。
2. `进一步讲解这个公式` 高置信度时直接分析，低置信度才确认。
3. 删除可见的“工作模式”单选框。
4. 把 `confirm-box` 从 `更多` 中移出，只作为需要确认时的当前步骤。
5. 在 `更多` 中加入 `打开练习页`，链接到服务端测试页。
6. 更新 NVDA 闭环测试文档，重点测试：
   - 首页只有一个清晰主动作。
   - 转译完成后 Tab 一步到 `进一步讲解这个公式`。
   - 点击后高置信度样例不再出现确认步骤。
   - 没有选中内容、受限页面、没有公式页面均有清晰反馈。
